# Ironclad release proposal — preparation only

This is a proposal for a later operator-reviewed release, not permission to deploy, publish, invite, notify, send, or activate a schedule. The cloud fixture, its credentials, and its volumes are not production inputs. The development branch is not a release artifact until its outstanding security, identity, source coverage, review, and end-to-end acceptance gaps are resolved.

1. **Inventory and provenance.** On the authorized host, identify the running image and commit, compose configuration, database and object-store locations, worker versions, existing service consumers and exact current source tree. Compare them with the reviewed commits without replacing independent host changes. Record hashes for the application, schema, migration, worker, dependency lock and corresponding-source package. Rebuild the licence inventory and notices for the actual release; the imported source manifest describes an older baseline.
2. **Protect state and rehearse.** Take consistent, encrypted, access-controlled local backups of PostgreSQL, object versions and metadata, application state, and configuration needed to restore service. Record backup time, integrity hashes, retention, ownership and the relationship between database rows and exact object versions. Keep credentials out of the package and logs. Restore copies into an isolated environment, verify byte hashes and representative document versions, and rehearse migration and rollback against those copies. A database-only backup is insufficient for stored files.
3. **Validate dependencies and access.** Resolve or explicitly assess the remaining dependency advisories and lint compatibility, then repeat build, security, browser, PDF worker and storage checks on the release tree. Verify scoped ClickUp/ERPNext inventories, archive and pagination controls, completion semantics, non-atomic read limitations and approved evidence sources in the authorized environment. Independently verify Swarm's snapshot schema, scope, provenance and read-only acquisition. Validate real reviewer authority and investor identity, expiry, revocation, room and media authorization before enabling any investor access. Synthetic tests do not establish these properties.
4. **Plan a controlled change.** Review schema migration compatibility, service startup ordering, storage capacity, worker queues, access controls and failure recovery against the current host. Stage the exact image and migration with outward actions disabled. Run dependent-service regressions for login, document upload and processing, versioned media, existing rooms and visitors, historical archive, storage, broker consumers and scheduled jobs without triggering messages, sync replay or cursor resets. Retain the prior image, configuration and versioned artifacts.
5. **Rollback and recovery.** Define a maintenance window and explicit stop criteria before any authorized change. If validation fails, stop the new services, restore the prior image/configuration and, if migration is incompatible, restore the coordinated database and object-store backup to a consistent point. Verify exact document bytes, permissions, worker processing and dependent services after restoration. Do not replay queues, overwrite newer objects or delete volumes as an implicit rollback. Record the result and reconcile any writes made since the backup under operator review.

Separate approvals are required for deployment and for each exact investor-visible candidate, audience and visibility. Any email requires its own exact subject, body and recipient approval. A successful rehearsal, specialist review, render or schedule does not authorize publication or sending.
